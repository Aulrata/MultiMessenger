# MultiMessenger

Внутренний сервис для менеджеров туристической компании: переписка с клиентами из
Telegram, WhatsApp и MAX в одном веб-интерфейсе, похожем на Telegram.

Требования — [docs/Техническое_задание.md](docs/Техническое_задание.md), порядок работ —
[docs/План_разработки.md](docs/План_разработки.md). Работа идёт строго по этапам плана;
критерии завершения этапа не пропускаются.

**Текущее состояние:** закрыты этапы 1.1–1.10 и 2.1–2.7. Следующий — 2.8, загрузка
истории при подключении. *Эту строку нужно обновлять при закрытии этапа.*

## Команды

Инфраструктура (приложение и Seq — в профилях, по умолчанию не поднимаются):

```bash
docker compose up -d
```

```bash
dotnet run --project src/MultiMessenger.Web
```

Сборка и тесты. **Обязательно `dotnet build` по всему решению:** `dotnet test` собирает
только тестовый проект и его зависимости, `MultiMessenger.Web` в них не входит, и ошибка
компиляции в разметке Blazor остаётся незамеченной.

```bash
dotnet build --configuration Release
```

```bash
dotnet test --configuration Release
```

Миграции:

```bash
dotnet ef migrations add <Имя> --project src/MultiMessenger.Infrastructure --startup-project src/MultiMessenger.Web --output-dir Persistence/Migrations
```


Зависимости строго `Web → Infrastructure → Core`. Нарушение ловит
`ProjectDependencyTests` — он читает `.csproj`, а не сборки.

## Соглашения проекта

**Версии пакетов только в `Directory.Packages.props`.** Указание версии в `.csproj`
даёт ошибку `NU1008`. `dotnet add package` работает правильно, если **не** передавать
`--no-restore`.

**FluentAssertions закреплён на 7.x.** С 8.0 платная лицензия для коммерческого
использования. Dependabot настроен не предлагать обновление.

**Ключи — Guid v7**, проставляются в инициализаторе свойства. Следствие: дочернюю
сущность к уже загруженному родителю добавлять только через `DbSet.Add` с явным внешним
ключом. `parent.Children.Add(...)` даст UPDATE несуществующей строки: EF видит
заполнённый ключ и считает запись существующей.

**Перечисления хранятся в БД строками**, не числами — журналы читают SQL-запросом.

**Время — `DateTimeOffset`**, всегда UTC. `Message.CreatedAt` — время по часам платформы,
не наше: иначе догрузка истории перемешает порядок переписки.

**Миграции применяются при старте** приложения. Это верно, пока экземпляр один.

**`DbContext` — и фабрика, и область.** Интерактивные страницы Blazor живут часами,
поэтому запросы кабинета создают контекст фабрикой на каждый вызов.

## Blazor: подводные камни, на которых уже спотыкались

**Интерактивность постраничная**, не глобальная. Формам входа, админки и интеграций
нужен `HttpContext` (выставить куку, взять адрес для аудита) — они статические.
Экран переписки интерактивный, `HttpContext` там недоступен, сотрудник берётся
из `AuthenticationState`.

**`[SupplyParameterFromQuery]` обязано быть `public`.** На приватном свойстве не
связывается молча, без предупреждения. У `[SupplyParameterFromForm]` приватные работают.

**Имя свойства с `[SupplyParameterFromForm]` должно совпадать с путём в разметке.**
Из него собирается префикс полей: свойство `CodeInput` → поле `CodeInput.Code`. Если
связать `_codeForm`, а в `InputText` написать `CodeInput.Code`, форма придёт пустой.

**Многошаговые статические формы держат состояние в адресной строке.** Blazor ищет
форму по имени **до** вызова обработчика: при POST компонент создаётся заново, и если
нужная форма не отрисована — «no form on the page currently has that name».

**Инициализатор у свойства формы вызывает `BL0008`.** Использовать ленивый геттер.

## Мессенджеры

**Типы платформ не выходят за пределы Infrastructure.** Ни `TL.*`, ни классы Baileys.
Остальная система работает только с `IMessengerConnector` и моделями из
`Core/Messaging`. От этого зависит, получится ли добавить WhatsApp и MAX на третьем
этапе, не переписывая интерфейс.

**Коннектор превращает любой сбой в результат, а не бросает.** Общий
`catch (Exception)` там нужен: иначе упадёт очередь отправки. Исключение — отмена,
она проходит наружу.

**Из фоновых служб исключения не выходят вообще.** Хост по умолчанию
останавливается на исключении в `BackgroundService` — один неисправный канал положил
бы веб-интерфейс. Уже случалось.

**`IMessengerConnectorFactory.Create` может бросить** — читает настройки платформы,
а `api_id`/`api_hash` на свежем сервере не заполнены. Защищать **каждое** место вызова.

**Telegram: `access_hash` берётся из списка диалогов при промахе кеша.** Личные
сообщения приходят формой `updateShortMessage`, где словаря `Users` нет — получить
хватает, ответить нет.

**Паузы в очереди исходящих — защита аккаунтов от блокировки, не оптимизация.**
Пауза при смене собеседника (25 с) отличается от паузы внутри диалога (3 с): перебор
получателей и есть признак рассылки. Отключать нельзя.

## Тесты

**База и хранилище — Testcontainers**, по одному контейнеру на коллекцию. Значит,
**база не пустая**: тест не должен предполагать, что видит только свои данные.
Фильтровать выборки по своим идентификаторам.

**Заготовки коннекторов — `tests/.../Messaging/FakeConnectors.cs`.** Методы, которые
подменяют наследники, должны быть `virtual`: вызовы идут через интерфейс, и сокрытие
через `new` не сработает.

**Время подменяется `TestTimeProvider`.** Проверять паузы очереди настоящим ожиданием
нельзя — они в десятки секунд.

**Живой Telegram в тестах не вызывается**: медленно, нестабильно, риск лимитов.
Проверять на настоящем аккаунте руками.

1. `dotnet build --configuration Release` по всему решению.
2. `dotnet test --configuration Release`.
3. Для кода, чувствительного к путям и локали, — прогон на Linux:
   ```bash
   docker run --rm -v "${PWD}:/src" -w /src mcr.microsoft.com/dotnet/sdk:10.0 dotnet test -c Release
   ```
4. Для страниц и форм — открыть в браузере. Три ошибки в форме интеграций
   собирались без единого предупреждения.
5. Версии сторонних действий GitHub — смотреть в реестре, а не по памяти.

## Безопасность

**Репозиторий публичный.**

**Файлы сессий равносильны полному доступу к аккаунтам менеджеров.** В `.gitignore`
правило `sessions/` **без ведущего слеша**: каталог создаётся рядом с приложением,
а не в корне. С `/sessions/` файл не игнорировался.

**Идентификаторы клиентов на платформе в технические логи не пишутся** — это
персональные данные, а логи уезжают в файлы и Seq на 30 дней.

**Обращение к чужой переписке фиксируется в аудите** (`ForeignDialogOpened`,
`MediaDownloaded`). Своё — нет, иначе журнал утонет.

**Выборки ограничены владельцем канала в самом запросе**, не в разметке.
