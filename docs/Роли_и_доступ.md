# Роли и доступ

Принятые решения по разграничению прав. Разделы про вход, роли и админку реализованы в этапе 1.5; мультиаккаунт — задел под этап 2.

## Роли вложены, а не разделены

Администратор — это менеджер с дополнительными правами. Он подключает свои каналы, ведёт свою переписку, отправляет сообщения; админка добавляется сверху и ничего не отнимает.

Технически: при входе администратору выдаются **обе** роли в claims — `Manager` и `Admin`. Тогда проверка рабочего кабинета пропускает его без перечисления ролей в каждом атрибуте.

```csharp
[Authorize(Roles = "Manager")]   // рабочий кабинет: обе роли
[Authorize(Roles = "Admin")]     // админка: только Admin
```

Вариант с `Roles = "Manager,Admin"` везде работает ровно до первого места, где второе значение забудут дописать.

## Интерфейс

| Раздел | Кто видит | Что можно |
|---|---|---|
| Рабочий кабинет | Manager, Admin | свои каналы, свои диалоги, отправка, правка, удаление |
| Админка | только Admin | создание и деактивация сотрудников, список сотрудников, дашборд состояния каналов, статистика |
| Чужая переписка (в админке) | только Admin | **только чтение** |

## Чужая переписка — режим чтения

Администратор видит переписку любого сотрудника, но поле ввода в этом режиме недоступно. Чтобы ответить, нужен явный переход в аккаунт сотрудника (см. ниже).

Разделение сделано осознанно: «посмотрел чужой чат» и «написал клиенту от чужого имени» — принципиально разные по последствиям действия, и в журнале они должны выглядеть по-разному, а не сливаться в одно.

Каждое открытие чужого диалога пишется в аудит как `ForeignDialogOpened`. Переписка с клиентами подпадает под 152-ФЗ: доступ к ней получает не только ведущий менеджер, значит на вопрос «кто и когда это читал» должен быть ответ.

## Мультиаккаунт

Вход в аккаунт другого сотрудника доступен **только роли Admin**. Сценарий — отпуск, больничный, увольнение: клиент пишет по своей заявке, а отвечать некому.

Список тех, кто может отвечать от чужого имени, совпадает со списком администраторов — отдельного уровня прав и экрана управления им не заводим.

В журнале фиксируется:

| Что | Где |
|---|---|
| вход в чужой аккаунт и выход | `AuditAction.ImpersonationStarted` / `ImpersonationEnded` |
| кто действовал | `AuditEntry.ManagerId` |
| под кем | `AuditEntry.ImpersonatedManagerId` |
| кто фактически отправил сообщение | `Message.SentByManagerId` |
| кто правил или удалял | `MessageEditHistory.ChangedByManagerId` |

Везде хранится фактический автор действия, а не владелец канала. Журнал отвечает на вопрос «кто это сделал», а не «под кем это выглядело».

## Удаление сообщений

Удаление через наш интерфейс происходит **у всех**: вызывается удаление на стороне платформы, и клиент перестаёт видеть сообщение. То есть `DeleteMessageAsync` в `IMessengerConnector` — реальная операция над платформой, а не пометка в своей БД.

Следствия для этапа 2:

- операция идёт через ту же очередь с rate-limiting, что и отправка, — платформа считает её обращением к API;
- отказ платформы (истекло окно, сообщение уже удалено) показывается менеджеру ошибкой, а не проглатывается;
- в нашей БД сообщение при этом остаётся: `Message.IsDeleted = true`, текст на момент удаления — в `MessageEditHistory`. Внутренний архив переписки не худеет от того, что запись убрали у клиента.
