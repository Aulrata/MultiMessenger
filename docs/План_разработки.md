# План разработки: MultiMessenger

Документ описывает пошаговый план реализации. Технические требования и модель данных — см. «Техническое задание: MultiMessenger — внутренний мультимессенджер компании».

**Общий принцип:** каждый этап заканчивается работающим состоянием, которое можно запустить и проверить. Не переходить к следующему этапу, пока критерии завершения текущего не выполнены.

**Стек:** ASP.NET Core (Web API + Blazor Server), PostgreSQL + EF Core, MinIO, WTelegramClient, BaileysCSharp, MAX REST API. Тесты — xUnit + FluentAssertions + Testcontainers.

# ЭТАП 1. Инфраструктура и каркас приложения

**Цель:** работающий скелет — приложение поднимается, видит БД и файловое хранилище, есть авторизация менеджера, есть пустой UI. Мессенджеров пока нет вообще.

## 1.1 Solution и структура проектов

Создать solution `MultiMessenger` с проектами:

| Проект | Тип | Назначение |
|---|---|---|
| `MultiMessenger.Core` | Class Library | Доменные сущности, интерфейсы (`IMessengerConnector`, `IFileStorage`), бизнес-логика. **Без** зависимостей на EF Core / ASP.NET |
| `MultiMessenger.Infrastructure` | Class Library | `AppDbContext` (EF Core), реализации коннекторов, реализация MinIO-хранилища |
| `MultiMessenger.Web` | ASP.NET Core (Blazor Server) | UI, API-эндпоинты, фоновые сервисы, точка входа |
| `MultiMessenger.Tests` | xUnit | Юнит- и интеграционные тесты |

Зависимости: `Web` → `Infrastructure` → `Core`. `Core` не зависит ни от чего.

**Пакеты:**
- `MultiMessenger.Infrastructure`: `Npgsql.EntityFrameworkCore.PostgreSQL`, `Microsoft.EntityFrameworkCore.Design`, `AWSSDK.S3` (для MinIO), `WTelegramClient`
- `MultiMessenger.Tests`: `xunit`, `FluentAssertions`, `NSubstitute` (или `Moq`), `Testcontainers.PostgreSql`

## 1.2 Инфраструктура в Docker

Создать `docker-compose.yml` в корне репозитория с сервисами:
- **postgres** (образ `postgres:16`), с именованным volume для данных, порт 5432 наружу
- **minio** (образ `minio/minio`), команда `server /data --console-address ":9001"`, volume для данных, порты 9000 (API) и 9001 (консоль)

Само приложение на этом этапе **запускается локально** через `dotnet run`, не в контейнере — так проще дебажить. Контейнеризация приложения выносится в раздел 1.7.

**Проверка:** `docker compose up -d`, оба контейнера в статусе healthy, консоль MinIO открывается в браузере на `localhost:9001`.

## 1.3 Конфигурация (заранее под будущий Docker)

Все внешние параметры — через `IConfiguration`, никакого хардкода в коде:

| Параметр | Пример локально | Пример на сервере |
|---|---|---|
| `ConnectionStrings:Postgres` | `Host=localhost;...` | `Host=postgres;...` |
| `Minio:Endpoint` | `localhost:9000` | `minio:9000` |
| `Telegram:ApiId` / `ApiHash` | из user-secrets | из переменных окружения |
| `Telegram:MTProxyUrl` | — | `https://t.me/proxy?...` |
| `Storage:SessionsBasePath` | `./sessions` | `/data/sessions` |

Секреты (`ApiHash`, пароли БД) локально — через `dotnet user-secrets`, на сервере — через переменные окружения. **Не коммитить в репозиторий.**

## 1.4 Модель данных и EF Core

1. Описать сущности из ТЗ как POCO-классы в `MultiMessenger.Core`: `Manager`, `MessengerAccount`, `Contact`, `ContactIdentity`, `Dialog`, `Message`, `MessageEditHistory`, `MediaAttachment`, `AccountHealthLog`.
2. Создать `AppDbContext` в `MultiMessenger.Infrastructure`, настроить связи и индексы через Fluent API:
   - Индекс на `Dialog.LastMessageAt` (сортировка списка диалогов)
   - Индекс на `Message.DialogId + CreatedAt` (выборка истории переписки)
   - **Уникальный** индекс на `Message.PlatformMessageId + DialogId` (защита от дублей при синхронизации)
   - Индекс на `ContactIdentity.Platform + PlatformUserId` (поиск контакта по входящему сообщению)
3. Первая миграция: `dotnet ef migrations add InitialCreate`, применить `dotnet ef database update`.
4. Настроить автоприменение миграций при старте приложения (`context.Database.Migrate()`), чтобы деплой не требовал ручных шагов.

**Проверка:** таблицы создались в Postgres, структура соответствует ТЗ.

## 1.5 Авторизация и роли

1. Экран логина: номер телефона + пароль. Хеширование пароля — `ASP.NET Core Identity` или `BCrypt`.
2. Две роли: `Admin`, `Manager`. Авторизация через cookie-аутентификацию.
3. Seed-скрипт (или консольная команда), создающий первого администратора при пустой БД.
4. Раздел админки (доступен только `Admin`): список менеджеров, создание учётной записи (ФИО, номер телефона, пароль), деактивация.

**Проверка:** админ создаёт менеджера через админку, менеджер входит под своими данными и видит пустой главный экран; менеджер не может открыть админку.

## 1.6 Файловое хранилище (абстракция + MinIO)

1. Интерфейс `IFileStorage` в `MultiMessenger.Core`: `SaveAsync(stream, key, contentType)`, `GetAsync(key)`, `DeleteAsync(key)`, `GetUrlAsync(key)`.
2. Реализация `MinioFileStorage` в `MultiMessenger.Infrastructure` через `AWSSDK.S3` (S3-совместимый клиент, указывающий на MinIO endpoint).
3. Эндпоинт отдачи файлов `GET /media/{id}` — проверяет права доступа (менеджер видит только свои вложения) и стримит файл из хранилища.

**Проверка:** тестовая загрузка/скачивание файла через `IFileStorage` работает; загруженный файл виден в консоли MinIO.

## 1.7 Контейнеризация приложения

1. `Dockerfile` для `MultiMessenger.Web` (multi-stage build: SDK для сборки → runtime-образ).
2. Добавить сервис `app` в `docker-compose.yml`, зависящий от `postgres` и `minio`, с volume для директории сессий.
3. Проверить полный запуск всего стека одной командой `docker compose up`.

## 1.8 Тесты этапа

- **Юнит:** валидация номера телефона, хеширование/проверка пароля, логика прав доступа (менеджер vs админ).
- **Интеграционные (Testcontainers):** применение миграций на чистой БД, базовые CRUD-операции через `AppDbContext`.

## 1.9 Логирование и аудит

Добавлено сверх исходного плана. Подробности — [Логирование.md](Логирование.md).

1. Структурированное логирование на Serilog: консоль, суточные JSON-файлы, опционально Seq.
2. Журнал аудита действий сотрудников в PostgreSQL — отдельно от технических логов.

## 1.10 CI/CD

1. Проверка на pull request: сборка решения и прогон тестов, включая интеграционные на Testcontainers.
2. Развёртывание на сервере при вливании в `main`: сборка образа, публикация в реестр, обновление стека на сервере.
3. Проверка живости после развёртывания и откат на предыдущий образ при неудаче.
4. Автообновление зависимостей.

- [x] Приложение стартует, применяет миграции, подключается к БД и MinIO
- [x] Админ создаёт менеджера, менеджер логинится по номеру и паролю
- [x] Разделение прав Admin/Manager работает

# ЭТАП 2. Telegram: полноценная работа одного мессенджера

**Цель:** менеджер подключает свой Telegram через веб-интерфейс и полноценно ведёт переписку в UI — с историей, медиа, real-time обновлениями и устойчивостью к обрывам.

## 2.1 Абстракция коннектора

Спроектировать в `MultiMessenger.Core` интерфейс, общий для всех платформ (реализовать пока только для Telegram):

```
IMessengerConnector
  - StartLoginAsync(...)         // начать подключение аккаунта
  - SubmitCodeAsync(...)          // подтвердить код
  - SubmitPasswordAsync(...)      // 2FA
  - ConnectExistingAsync(...)      // поднять по сохранённой сессии
  - SendMessageAsync(...)          // отправить текст/медиа
  - DisconnectAsync(...)
  - событие OnIncomingMessage / OnMessageEdited / OnReadStatusChanged
```

**Важно:** остальная система (UI, воркеры, БД) работает только с этим интерфейсом и с нормализованными моделями сообщений — никаких типов из `WTelegramClient` за пределами `MultiMessenger.Infrastructure`. От этого зависит лёгкость добавления WhatsApp и MAX на этапе 3.

## 2.2 Telegram-коннектор

1. Реализация `TelegramConnector` поверх `WTelegramClient`.
2. Вход **по номеру телефона** (не QR — по рекомендации авторов библиотеки, QR-логин для юзерботов повышает риск бана).
3. MTProxy-подключение через `client.MTProxyUrl` из конфигурации.
4. Хранение файла сессии по пути из `Storage:SessionsBasePath`, имя файла — по `MessengerAccount.Id`.
5. Нормализация входящих: из объектов MTProto в общую модель (`Platform`, `PlatformUserId`, `PlatformMessageId`, текст, вложения, время).

## 2.3 Менеджер живых подключений (Hosted Service)

1. `AccountConnectionManager` — синглтон, хранит словарь «id аккаунта → активный коннектор».
2. `BackgroundService`, который при старте приложения поднимает все `MessengerAccount` со статусом `Active` через `ConnectExistingAsync`.
3. Регистрация обработчиков событий коннектора → запись в БД.

## 2.4 Флоу подключения аккаунта через UI

Раздел «Интеграции» в кабинете менеджера:
1. Форма ввода номера (предзаполнена номером из профиля менеджера) → `StartLoginAsync`.
2. Экран ввода кода → `SubmitCodeAsync`.
3. Экран ввода пароля 2FA (если требуется) → `SubmitPasswordAsync`.
4. При успехе — создание записи `MessengerAccount` со статусом `Active`, регистрация в `AccountConnectionManager`.
5. Незавершённые попытки логина хранятся во временном состоянии с таймаутом (5–10 минут), после чего очищаются фоновой задачей.

**Проверка:** новый Telegram-аккаунт подключается полностью через браузер, без единой строки кода и без доступа к серверу.

## 2.5 Приём входящих сообщений (Inbox)

1. Обработчик события коннектора → найти/создать `Contact` + `ContactIdentity` по `PlatformUserId` → найти/создать `Dialog` → сохранить `Message`.
2. Обновить `Dialog.LastMessageAt` и `Contact.PrimaryPlatform`.
3. Опубликовать внутреннее событие для UI (адресно — конкретному менеджеру-владельцу аккаунта).

## 2.6 Отправка исходящих (Outbox)

1. Менеджер отправляет сообщение в UI → запись в `Message` со статусом `Pending`, немедленное отображение в интерфейсе.
2. `OutboxWorker` (`BackgroundService`) выбирает `Pending`-сообщения и отправляет через коннектор.
3. **Rate-limiting:** отдельная очередь на каждый аккаунт, пауза между отправками (стартовое значение ~20–30 сек между сообщениями разным получателям, настраиваемое через конфиг).
4. По результату: статус → `Sent` (+ проставить `PlatformMessageId`) или `Failed` (+ причина, отображается в UI).

## 2.7 UI: главный экран (в стиле Telegram)

1. Левая колонка: список диалогов, отсортированный по `LastMessageAt` (по убыванию), со счётчиком непрочитанных.
2. Правая часть: история переписки выбранного диалога с пагинацией/подгрузкой при прокрутке вверх.
3. Поле ввода: текст, прикрепление файла, запись/отправка голосового.
4. Real-time обновление через встроенный SignalR Blazor Server — при новом сообщении экран обновляется без перезагрузки; события адресуются конкретному менеджеру, а не широковещательно.
5. Карточка контакта: имя (редактируемое), номер заявки CRM (`CrmOrderNumber`), заметки.

> Раскладка списка и поведение при нескольких платформах уточнены в [Интерфейс_переписки.md](Интерфейс_переписки.md): список строится по контактам, переписки по платформам не смешиваются в одну ленту.

## 2.8 Загрузка истории при первом подключении

1. Фоновая задача после успешного логина: обход диалогов аккаунта и загрузка истории сообщений в БД.
2. Индикация прогресса в UI («Загружено N из ~M»).
3. Идемпотентность: повторный запуск не должен создавать дубли (защита уникальным индексом по `PlatformMessageId + DialogId`).

## 2.9 Медиа (фото, голосовые, документы)

1. **Входящие:** при получении медиа-сообщения скачать файл через коннектор → сохранить в MinIO → создать `MediaAttachment` со ссылкой (`StorageKey`).
2. **Исходящие:** файл из UI → в MinIO → передать в коннектор при отправке.
3. Для голосовых сохранять `DurationSeconds` — нужно для отображения дорожки в UI.
4. UI отображает медиа **только** через собственный эндпоинт `/media/{id}`, не по ссылкам мессенджера (они истекают).

## 2.10 Синхронизация с официальным клиентом (мультиустройство)

Реализовать логику из раздела 5.6 ТЗ:
1. Обрабатывать не только входящие, но и события с флагом `out_ = true`.
2. Сопоставление по `PlatformMessageId`: совпало с записью из Outbox → обновить статус; не совпало → создать новую исходящую запись (сообщение отправлено вручную с телефона).
3. Подписка на серверные события прочтения → обновление счётчиков непрочитанных.
4. Обработка событий редактирования: старый текст → `MessageEditHistory`, актуальный → в `Message`, флаг `IsEdited`.

## 2.11 Устойчивость и мониторинг

1. `HealthCheckWorker`: периодическая проверка состояния каждого активного коннектора.
2. Автопереподключение при обрыве с экспоненциальным backoff (5с → 30с → 2мин → 10мин).
3. При невалидной сессии (реальный логаут, а не обрыв) — статус `RequiresReauth` + уведомление менеджера в UI.
4. Логирование событий в `AccountHealthLog`.
5. Дашборд в админке: статус каждого аккаунта, время последней активности, счётчик `Failed`-отправок, объём сообщений за день/неделю.

## 2.12 Резервное копирование

Настроить на сервере регулярную задачу (cron), выгружающую **за пределы основного сервера**: директорию сессий, дамп PostgreSQL, содержимое MinIO (`mc mirror`). Снапшоты хостера — дополнительный, а не единственный уровень защиты.

## 2.13 Тесты этапа

- **Юнит (приоритет — самая хрупкая логика):**
  - Дедупликация по `PlatformMessageId` (свой Outbox vs внешнее сообщение с телефона)
  - Rate-limiting: выдерживаются ли паузы между отправками
  - Нормализация входящих: из платформенной модели в доменную
  - Обновление `PrimaryPlatform` контакта
- **Интеграционные (Testcontainers):** сохранение сообщения с вложением, выборка списка диалогов с правильной сортировкой, идемпотентность загрузки истории.
- **Не тестировать автоматически:** реальные вызовы к Telegram (медленно, нестабильно, риск rate-limit) — коннектор подменяется fake-реализацией через `IMessengerConnector`.

## ✅ Критерии завершения этапа 2
- [ ] Менеджер подключает Telegram полностью через веб-интерфейс
- [ ] История переписки подгружается при подключении, без дублей
- [ ] Входящие появляются в UI в реальном времени
- [ ] Исходящие уходят через очередь с rate-limiting, статусы отображаются
- [ ] Фото, голосовые и документы отправляются и принимаются
- [ ] Сообщение, отправленное с телефона, появляется в системе (без дубля)
- [ ] Обрыв соединения → автоматическое восстановление
- [ ] Дашборд показывает статусы аккаунтов
- [ ] Бэкапы настроены и проверены восстановлением

# ЭТАП 3. WhatsApp и MAX

**Цель:** добавить две платформы, не переделывая UI и модель данных. Если на этом этапе приходится менять что-то за пределами новых коннекторов — значит, абстракция из 2.1 была спроектирована недостаточно; это сигнал вернуться и доработать её.

## 3.1 WhatsApp-коннектор

### 3.1.1 Подключение
1. Реализация `WhatsAppConnector` через `BaileysCSharp` под тем же интерфейсом `IMessengerConnector`.
2. Вход **через QR-код** (в отличие от Telegram): генерация QR в UI (`QRCoder`), отображение в разделе «Интеграции», ожидание сканирования, обработка успеха/таймаута.
3. Хранение состояния авторизации в директории сессий (аналогично Telegram).

### 3.1.2 Особенности платформы
1. **История ограничена** окном, которое отдаёт протокол WhatsApp Web (не вся переписка за все годы) — заложить это в UI-текст при подключении, чтобы менеджер не ожидал полной выгрузки.
2. Медиа: скачивание входящих вложений и отправка исходящих через API библиотеки, далее — стандартный путь через `IFileStorage`.
3. Идентификатор пользователя — WhatsApp JID, сохраняется в `ContactIdentity.PlatformUserId`.

### 3.1.3 Устойчивость
Подключить к тем же механизмам, что и Telegram: `AccountConnectionManager`, `OutboxWorker` с rate-limiting, `HealthCheckWorker` с backoff, `AccountHealthLog`.

**Проверка:** менеджер подключает WhatsApp по QR, переписка ведётся в том же UI, что и Telegram.

## 3.2 MAX-коннектор

### 3.2.1 Принципиальное отличие
MAX работает **через ботов** (REST API + входящий вебхук), а не через эмуляцию личного аккаунта. Нет постоянного соединения, нет файла сессии, подключение — по токену бота.

### 3.2.2 Подключение
1. Инструкция в UI: менеджер создаёт бота через `@MasterBot` в приложении MAX и получает токен.
2. Форма вставки токена → сохранение в `MessengerAccount.BotToken` → валидация токена запросом к API.
3. Регистрация вебхука в MAX на публичный URL сервиса.

### 3.2.3 Приём сообщений
1. Эндпоинт `POST /webhooks/max/{accountId}` — принимает события от MAX.
2. **Обязательно:** проверка подлинности запроса (секрет/подпись), чтобы эндпоинт нельзя было дёргать снаружи произвольными данными.
3. Нормализация в общую доменную модель → далее стандартный путь Inbox.

### 3.2.4 Ограничения (заложить в UI и ожидания)
1. **История недоступна ретроактивно** — бот видит только сообщения с момента подключения. Отобразить это в интерфейсе при подключении MAX.
2. Проверить актуальные требования MAX к публикации ботов (по документации — верификация юрлица РФ) до начала интеграции.

**Проверка:** сообщение, отправленное клиентом боту в MAX, появляется в общем UI; ответ менеджера доходит до клиента.

## 3.3 Мультиплатформенность на уровне клиента

1. Логика связывания: один `Contact` — несколько `ContactIdentity` на разных платформах.
2. Автообновление `Contact.PrimaryPlatform` при каждом входящем (платформа последнего сообщения).
3. UI переписки:
   - явная пометка платформы у каждого сообщения (иконка/бейдж);
   - выбор платформы для ответа, по умолчанию — `PrimaryPlatform`;
   - объединённая карточка контакта со всеми его каналами.
4. Ручное слияние двух контактов в один (когда система не смогла определить, что это один человек) — минимально: выбрать контакты, подтвердить объединение, перепривязать `ContactIdentity` и диалоги.

## 3.4 Поиск

1. Полнотекстовый поиск средствами PostgreSQL: колонка `tsvector` по тексту сообщений + GIN-индекс, обновление через триггер или при сохранении.
2. Поиск по контактам: имя, номер телефона, `CrmOrderNumber`.
3. UI: строка поиска с результатами по обоим направлениям (сообщения и контакты), с переходом к нужному месту переписки.

## 3.5 Привязка к CRM (U-ON)

На этом этапе — только ручная привязка: поле `CrmOrderNumber` в карточке контакта, доступное для ввода и поиска. Двусторонняя интеграция с API U-ON выносится в отдельную задачу за рамками текущего плана.

## 3.6 Тесты этапа

- **Юнит:** нормализация входящих для каждой новой платформы (WhatsApp JID, MAX-события), логика выбора платформы для ответа, обновление `PrimaryPlatform`.
- **Интеграционные:** обработка вебхука MAX (включая отклонение запроса с неверной подписью), связывание контакта по нескольким `ContactIdentity`, корректность полнотекстового поиска.

## ✅ Критерии завершения этапа 3
- [ ] WhatsApp подключается по QR, переписка работает в общем UI
- [ ] MAX подключается по токену бота, вебхук принимает и проверяет подпись
- [ ] Клиент, писавший с двух платформ, отображается одним контактом
- [ ] Менеджер видит платформу каждого сообщения и выбирает, куда отвечать
- [ ] Поиск по сообщениям и контактам работает
- [ ] Добавление платформ не потребовало изменений в UI-компонентах и схеме БД (кроме расширения enum платформ)

# Приложение: сквозные правила разработки

## Порядок работы
1. Не переходить к следующему этапу, пока не выполнены критерии завершения текущего.
2. Внутри этапа — двигаться вертикальными срезами: быстро получить сквозной рабочий путь, затем полировать (обработка ошибок, edge-кейсы, UI).
3. Первая версия каждого шага может быть грубой — важнее рабочий скелет, чем идеальный код на старте (это MVP).

## Правила, облегчающие деплой
1. Все внешние параметры — через конфигурацию, никакого хардкода `localhost` и путей к файлам.
2. Секреты (`ApiHash`, пароли) — user-secrets локально, переменные окружения на сервере. **Никогда в репозиторий.**
3. Миграции применяются автоматически при старте приложения.

## Безопасность
1. Файлы сессий = полный доступ к аккаунтам. Ограничить права доступа на уровне ОС, рассмотреть шифрование, хранить ключ отдельно.
2. `api_id`/`api_hash` — один на весь сервис (изоляция аккаунтов обеспечивается разными файлами сессий, а не разными `api_id`).
3. Эндпоинт вебхука MAX — обязательная проверка подписи.
4. Эндпоинт отдачи медиа — проверка прав: менеджер видит только вложения своих диалогов.

## Работа с риском блокировки аккаунтов
1. Rate-limiting в Outbox — не отключать «для скорости».
2. Не рассылать одинаковые тексты массово; сервис предназначен для переписки 1-на-1.
3. Не пересоздавать сессии без необходимости — частые перелогины повышают подозрительность.
4. Учитывать, что активность из официального клиента и из системы суммируется для лимитов платформы.
5. Мониторить статусы через дашборд, чтобы замечать проблему раньше, чем пожалуется клиент.
