# Техническое задание: MultiMessenger — внутренний мультимессенджер компании

## 1. Общее описание

Внутренний сервис для сотрудников (менеджеров) компании, объединяющий переписку с клиентами из **Telegram**, **WhatsApp** и **MAX** в едином веб-интерфейсе, похожем по UX на Telegram. Каждый менеджер работает под своим рабочим номером телефона, привязанным к соответствующим мессенджер-аккаунтам. Все входящие и исходящие сообщения проходят через центральную БД, что даёт единую точку правды, историю переписки и задел под дальнейшую интеграцию с CRM (U-ON).

---

## 2. Технологический стек

| Слой | Технология | Комментарий |
|---|---|---|
| Бэкенд | ASP.NET Core (Web API + Hosted/Background Services) | Единый процесс: API, фоновые мессенджер-клиенты, вебхуки |
| UI | Blazor Server | Real-time обновления через встроенный SignalR без написания JS |
| БД | PostgreSQL | Хранение сообщений, диалогов, аккаунтов, контактов; полнотекстовый поиск (`tsvector` + GIN) |
| Файловое хранилище | MinIO (S3-совместимое, self-hosted) | Фото, голосовые, документы. Доступ через абстракцию `IFileStorage`, чтобы позже можно было переключиться на внешний S3 без изменения бизнес-логики |
| Telegram-клиент | WTelegramClient (MTProto, C#) | Один `Client` на аккаунт, вход по номеру телефона (не QR — риск бана) |
| WhatsApp-клиент | BaileysCSharp (или обёртка над Baileys) | Один сокет-клиент на аккаунт, вход по QR |
| MAX-клиент | Собственная реализация поверх REST API (`platform-api2.max.ru`) | Работает как бот, приём событий через входящий вебхук, а не постоянное соединение |
| Прокси/сеть | Собственный MTProxy на VPS в Германии | Обход блокировок для Telegram-клиентов; тот же сервер хостит всё приложение |
| Резервное копирование | cron + rsync/mc mirror на внешнее хранилище | Сессии, БД, содержимое MinIO — вне основного сервера |

---

## 3. Архитектура (слои)

1. **Слой коннекторов платформ** — по одной реализации на Telegram / WhatsApp / MAX за общим интерфейсом (подключение аккаунта, приём входящих, отправка исходящих). Скрывает от остальной системы протокольные различия платформ.
2. **Слой фоновых воркеров (Hosted Services)**
   - Менеджер живых клиентов Telegram/WhatsApp (держит соединения, реагирует на апдейты)
   - Health-check / auto-reconnect джоба с экспоненциальным backoff
   - Очередь исходящих сообщений (Outbox) с rate-limiting на аккаунт
   - Загрузчик истории при первом подключении (Telegram — полная история, WhatsApp — доступное окно)
3. **Слой данных** — PostgreSQL (структурированные данные) + MinIO (бинарные файлы) за абстракцией хранилища.
4. **Слой API/UI** — Blazor Server-компоненты, обращающиеся только к БД и внутренним сервисам, никогда напрямую к Telegram/WhatsApp/MAX.
5. **Слой администрирования** — отдельная секция (доступна только роли Admin): создание менеджеров, дашборд состояния аккаунтов, статистика по сообщениям.

**Принцип Inbox/Outbox:** все сообщения — и входящие, и исходящие — сначала попадают в БД, и только потом (или только оттуда) идёт реальная работа с мессенджером. UI никогда не работает с "сырыми" объектами платформ напрямую.

| CreatedAt | — |

| Id | Идентификатор |

| DisplayNameOnPlatform | Имя/username, как оно видно на этой платформе |

| Поле | Описание |

| Поле | Описание |

## 5. Бизнес-процессы

### 5.1 Авторизация менеджера
Внутреннее приложение без самостоятельной регистрации. Админ через админку создаёт учётную запись менеджера, указывая его **рабочий номер телефона** (выданный компанией) как логин, и задаёт/генерирует пароль. Номер логина в системе совпадает с номером, который затем используется для подключения Telegram и WhatsApp этого менеджера.

### 5.2 Подключение мессенджер-аккаунта
Раздел «Интеграции» в личном кабинете менеджера, флоу зависит от платформы:

- **Telegram / WhatsApp** — форма «номер телефона → код подтверждения → (пароль 2FA при необходимости)» для Telegram; QR-код для WhatsApp. После успеха создаётся файл сессии, аккаунт переходит в фоновый режим постоянной работы.
- **MAX** — менеджер создаёт бота через @MasterBot в самом MAX, получает токен и вставляет его в форму подключения. Постоянное соединение не требуется — регистрируется входящий вебхук.

### 5.3 Загрузка истории при подключении
- **Telegram** — фоновая задача подгружает полную доступную историю диалогов после успешной авторизации, с индикацией прогресса в UI.
- **WhatsApp** — синхронизируется история в пределах окна, предоставляемого протоколом WhatsApp Web (не бесконечная вглубь — ограничение самого протокола).
- **MAX** — история пополняется только с момента добавления бота в переписку; ретроактивная выгрузка старых сообщений технически недоступна через бот-API.

### 5.4 Приём и отправка сообщений (Inbox/Outbox паттерн)
- **Входящие**: сообщение от платформы → сразу пишется в БД (таблица `Message`) → UI менеджера обновляется в реальном времени через SignalR, перечитывая данные из БД.
- **Исходящие**: менеджер отправляет сообщение → сразу сохраняется в БД со статусом `Pending`, мгновенно отображается в интерфейсе → фоновый воркер очереди берёт `Pending`-сообщения, применяет rate-limiting (пауза между отправками на аккаунт) и реально отправляет через API нужной платформы → статус обновляется на `Sent`/`Failed`.
- Такой подход даёт единую точку правды для UI (он никогда не общается с мессенджерами напрямую) и защищает от потери сообщений при сетевых сбоях.

### 5.5 Работа с медиа (фото, голосовые, документы)
Единая абстракция хранилища (`IFileStorage`) поверх MinIO. При получении медиа-сообщения файл скачивается с платформы и сохраняется в MinIO, в БД — только ссылка (`StorageKey`). При отправке — файл сначала загружается менеджером в MinIO через интерфейс, затем передаётся в API платформы. UI всегда отображает медиа из собственного хранилища, а не по временным ссылкам мессенджеров (которые могут истекать).

### 5.6 Синхронизация с официальными клиентами (мультиустройство)

Менеджеры могут параллельно пользоваться официальным приложением Telegram/WhatsApp на своём телефоне — система должна учитывать это, а не считать себя единственным источником сообщений на аккаунте.

**Техническая основа.** Подключение через WTelegramClient/Baileys добавляется как ещё одно устройство к аккаунту (аналогично «Настройки → Устройства» в обычном приложении) и работает параллельно с официальным клиентом без конфликтов на уровне протокола — это штатный, предусмотренный сценарий.

**Обработка исходящих, отправленных не через систему.** Обработчик входящих апдейтов должен учитывать не только «чужие» входящие сообщения (`out_ = false`), но и события с флагом `out_ = true` — они означают, что сообщение отправлено с этого аккаунта (в том числе вручную, из другого устройства). Такие события нужно сопоставлять с уже существующими записями в БД по `PlatformMessageId`:
- если `PlatformMessageId` совпадает с записью, ранее созданной через собственную очередь отправки (Outbox) — это подтверждение уже известного сообщения, нужно только обновить его статус (`Sent`) и проставить `PlatformMessageId`, если он ещё не был проставлен;
- если совпадения нет — сообщение отправлено вручную, из другого клиента менеджера (например, с телефона), и его нужно создать в БД как новую исходящую запись, чтобы в истории переписки внутри системы не образовывалось «дыр».

**Дедупликация.** Ключ сопоставления — `PlatformMessageId`. До получения подтверждения от платформы отправленное через Outbox-очередь сообщение хранится в БД со статусом `Pending` и временным локальным идентификатором; после подтверждения запись обновляется, а не дублируется.

**Синхронизация статусов прочтения.** Если менеджер читает сообщения в официальном приложении, Telegram/WhatsApp помечают их прочитанными на сервере независимо от веб-интерфейса системы. Чтобы счётчики непрочитанных сообщений в системе не расходились с реальностью, коннектор должен также подписываться на серверные события прочтения (не только на новые сообщения) и обновлять статус соответствующих записей в БД.

**Общий «бюджет доверия» аккаунта.** Активность из официального клиента и из системы суммируется с точки зрения платформы — это не создаёт проблем при обычной переписке 1-на-1, но стоит учитывать при любых сценариях массовой отправки: лимиты и репутационные риски общие для аккаунта, а не разделены по источнику отправки.

### 5.7 Редактирование сообщений
При получении события редактирования от платформы старое содержимое переносится в `MessageEditHistory`, актуальный текст обновляется в основной записи `Message`. Менеджер всегда видит актуальную версию сообщения — как в оригинальном клиенте Telegram/WhatsApp, — при этом полная история правок сохраняется в БД.

### 5.8 Работа с клиентом, пишущим с нескольких платформ
Один `Contact` может иметь несколько записей `ContactIdentity` — по одной на каждую платформу, с которой писал клиент. Поле `Contact.PrimaryPlatform` автоматически обновляется на платформу последнего входящего сообщения. В интерфейсе переписки менеджер:
- видит явную пометку, с какой платформы пришло каждое сообщение;
- может выбрать платформу для ответа вручную (если у клиента несколько активных каналов), с платформой по умолчанию, предзаполненной из `PrimaryPlatform`.

### 5.9 Привязка к CRM (задел под U-ON)
Менеджер может вручную привязать к контакту номер заявки (`CrmOrderNumber`). Поле хранится как простой текст на данном этапе — точная интеграция с API U-ON (двусторонняя синхронизация статусов и т.д.) выносится в отдельную последующую задачу.

### 5.10 Поиск
Полнотекстовый поиск средствами PostgreSQL (`tsvector` + GIN-индекс) по тексту сообщений; отдельный поиск по контактам (имя, номер заявки CRM). Для текущего масштаба (10 менеджеров) выделенный поисковый движок (Elasticsearch и т.п.) избыточен.

### 5.11 Мониторинг и восстановление аккаунтов
Фоновая health-check джоба периодически проверяет состояние каждого `MessengerAccount`. При обрыве — попытка автопереподключения по сохранённой сессии с экспоненциальным backoff (5с → 30с → 2мин → 10мин), чтобы не создавать паттерн аномальной активности. Если сессия невалидна (не временный обрыв, а реальный логаут) — статус аккаунта переводится в `RequiresReauth`, событие логируется в `AccountHealthLog`. Дашборд в админке отображает: статус каждого аккаунта, время последней активности, количество сообщений за день/неделю по менеджеру, счётчик неудачных отправок.

### 5.12 Резервное копирование
Регулярная (например, ежедневная) job выгружает за пределы основного сервера: файлы сессий Telegram/WhatsApp, дамп PostgreSQL, содержимое MinIO — на внешнее хранилище или личный компьютер/NAS администратора. Снапшоты уровня хостинг-провайдера используются как дополнительный, а не единственный уровень защиты.

## 6. Открытые вопросы и риски

- **Неофициальные протоколы Telegram/WhatsApp** — оба клиента эмулируют поведение официального приложения в обход предусмотренных ToS способов автоматизации, что несёт риск блокировки аккаунтов. Используемые номера уже 2+ года в органической эксплуатации без спама, что существенно снижает базовый риск, но требования по rate-limiting между сообщениями и мониторингу статуса аккаунтов (см. 5.11) остаются актуальными при любом стаже номера. Отдельно учтено, что менеджеры могут параллельно пользоваться официальными клиентами на этих же номерах (см. 5.6) — активность из обоих источников суммируется с точки зрения лимитов платформы.
- **MAX и юрлица** — по состоянию на актуальную документацию, публикация ботов MAX ограничена верифицированными юрлицами РФ — стоит уточнить процесс регистрации именно для сценария компании.
- **Хранение персональных данных клиентов** — переписка подпадает под требования 152-ФЗ; стоит заранее определить основания обработки и процесс на случай запроса удаления данных клиентом.
- **Рост объёма медиафайлов** — при текущих вводных ориентировочно ~100 ГБ/год; корректировать план хранения по мере накопления реальной статистики использования.
