# Логирование и аудит

В системе два независимых потока событий. Их легко перепутать, но требования к ним противоположные.

| | Технические логи | Аудит действий |
|---|---|---|
| Что пишем | запросы, ошибки, переподключения коннекторов, работа воркеров | вход в систему, открытие диалога, отправка сообщения, изменения в админке |
| Зачем | разобраться, почему сломалось | ответить, кто и когда что сделал |
| Где живут | файлы + Seq | таблица `AuditEntry` в PostgreSQL |
| Срок хранения | 30 дней, ротация | годы, вместе с остальными данными |
| Потеря записи | допустима | недопустима |
| Как читаем | Seq, `jq` по файлам | SQL, выгрузка из админки |

## Технические логи

Работают на Serilog, настраиваются секцией `Serilog` в `appsettings.json` — уровни и sink'и меняются без пересборки.

**Console** — человекочитаемый вывод, основное средство при локальной разработке и `docker logs` на сервере.

**File** — `logs/multimessenger-YYYYMMDD.jsonl`, формат CompactJsonFormatter: одно событие на строку, структурированные свойства сохранены. Ротация ежедневная, хранится 30 файлов, лимит 100 МБ на файл. Этот sink работает всегда — он не зависит от внешних сервисов и попадает в бэкап.

Строка выглядит так:

```json
{"@t":"2026-08-15T16:43:45.6391166Z","@mt":"HTTP {RequestMethod} {RequestPath} responded {StatusCode} in {Elapsed:0.0000} ms","RequestMethod":"GET","RequestPath":"/","StatusCode":200,"Elapsed":131.857,"SourceContext":"Serilog.AspNetCore.RequestLoggingMiddleware"}
```

Свойства лежат отдельными полями, а не запечены в текст, поэтому файл фильтруется `jq`:

```bash
jq -c 'select(.StatusCode >= 500)' logs/multimessenger-20260815.jsonl
```

**Seq** — веб-интерфейс поверх тех же событий: фильтры по любому свойству (`StatusCode >= 500`, `ManagerId = '...'`), группировка, графики, выгрузка в CSV/JSON. Подключается, только если задан `Seq:ServerUrl`; по умолчанию пусто, и приложение никуда не стучится.

Поднять локально:

```bash
docker compose --profile observability up -d
```

Затем включить отправку (значение не секрет, но зависит от машины — поэтому в user-secrets):

```bash
dotnet user-secrets set "Seq:ServerUrl" "http://localhost:5341" --project src/MultiMessenger.Web
```

Интерфейс — `http://localhost:5341`, логин `admin`, пароль из `SEQ_ADMIN_PASSWORD` в `.env`.

Файловый sink при этом никуда не девается: Seq — это удобство, а не единственная копия. Если контейнер упадёт или его удалят вместе с volume, история останется в файлах.

> Лицензия Seq бесплатна с ограничением по числу пользователей. Перед выкаткой на сервер стоит свериться с текущими условиями. Если условия не подойдут, альтернатива — Grafana Loki: полностью открытая, но тяжелее в настройке и хуже понимает структурированные свойства .NET.

## Аудит действий

Модель — `MultiMessenger.Core.Auditing`: сущность `AuditEntry`, перечисление `AuditAction`, интерфейс `IAuditTrail`.

Хранится в PostgreSQL по трём причинам:

1. **Связи.** Нужен FK на менеджера и выборки «все действия сотрудника за месяц».
2. **Сохранность.** Запись попадает в тот же дамп БД, что и переписка. Ротация логов её не затронет.
3. **152-ФЗ.** Переписка с клиентами — персональные данные. Вопрос «кто из сотрудников открывал этот диалог» должен иметь ответ, а не «где-то в логах за прошлый квартал, если они не ротировались».

Поле `DetailsJson` кладётся в колонку `jsonb`, так что по подробностям события можно фильтровать SQL-запросами, не заводя отдельных колонок под каждый тип действия.

Реализация `IAuditTrail` появляется на этапе 1.4 вместе с `AppDbContext`, первые записи — на 1.5 (вход, выход, неудачная попытка входа). Дальше список пополняется по мере появления функциональности: подключение канала (2.4), отправка сообщения (2.6), слияние контактов (3.3).

### События повышенной чувствительности

Три действия выделены отдельно, потому что затрагивают чужие данные:

| Действие | Когда пишется |
|---|---|
| `ForeignDialogOpened` | администратор открыл переписку другого сотрудника |
| `ImpersonationStarted` / `ImpersonationEnded` | вход в аккаунт другого сотрудника и возврат в свой |

У `AuditEntry` для этого есть два поля: `ManagerId` — кто действовал на самом деле, `ImpersonatedManagerId` — под кем. Разделение принципиальное: журнал должен отвечать на вопрос «кто это сделал», а не «под кем это выглядело». Та же логика в `Message.SentByManagerId` и `MessageEditHistory.ChangedByManagerId` — там хранится фактический автор действия, а не владелец канала.

### Изменения и удаления сообщений

Правки и удаления живут не в аудите, а в `MessageEditHistory` — это часть истории переписки, а не журнал доступа. Каждая запись хранит `ChangeType` (правка или удаление), `Origin` (клиент, менеджер через наш интерфейс, менеджер со своего телефона) и текст до изменения. Само сообщение при удалении помечается `IsDeleted`, но из таблицы не исчезает.

В аудит при этом тоже уходит запись — `MessageEdited` / `MessageDeleted`, но только для действий через наш интерфейс: удаление клиентом на его стороне не является действием сотрудника и в журнале доступа ему не место.

**Важное событие пишется в оба потока.** Неудачная попытка входа идёт и в технический лог (чтобы увидеть всплеск при подборе пароля), и в аудит (чтобы разбирать инцидент через полгода). Дублирование здесь осознанное.
