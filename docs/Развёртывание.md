# Развёртывание

## Как это работает

```
pull request → CI (сборка + тесты + проверка Dockerfile)
     ↓ merge в main
Deploy: тесты → образ в GHCR → ssh на сервер → docker compose up → проверка готовности
                                                        ↓ не поднялось
                                                   откат на предыдущий образ
```

Миграции применяются самим приложением при старте, поэтому выкатка — это просто подмена образа и перезапуск контейнера. Отдельного шага с БД нет.

## Что уже настроено

| Файл | Назначение |
|---|---|
| [.github/workflows/ci.yml](../.github/workflows/ci.yml) | pull request в `main` или `dev`: сборка, тесты, проверка сборки образа |
| [.github/workflows/deploy.yml](../.github/workflows/deploy.yml) | push в `main`: публикация образа и выкатка |
| [.github/dependabot.yml](../.github/dependabot.yml) | еженедельные обновления NuGet, ежемесячные — actions и базовых образов |
| [Dockerfile](../Dockerfile) | multi-stage сборка, запуск не от root |
| [deploy/docker-compose.prod.yml](../deploy/docker-compose.prod.yml) | боевой стек, кладётся на сервер |

## Что нужно сделать на сервере — один раз

1. Установить Docker и docker compose.
2. Создать каталог развёртывания, например `/opt/multimessenger`.
3. Положить туда `docker-compose.prod.yml` из каталога `deploy`.
4. Создать рядом `.env` с боевыми значениями:

```
POSTGRES_DB=multimessenger
POSTGRES_USER=multimessenger
POSTGRES_PASSWORD=<сильный пароль>
MINIO_ROOT_USER=<логин>
MINIO_ROOT_PASSWORD=<сильный пароль>
TELEGRAM_API_ID=<из my.telegram.org>
TELEGRAM_API_HASH=<из my.telegram.org>
SEED_ADMIN_PHONE=+7...
SEED_ADMIN_PASSWORD=<пароль первого администратора>
```

5. Создать пользователя для развёртывания и SSH-ключ **без пароля** — пайплайн не умеет вводить парольную фразу.

## Секреты в GitHub

`Settings → Secrets and variables → Actions`:

| Секрет | Значение |
|---|---|
| `DEPLOY_HOST` | адрес сервера |
| `DEPLOY_USER` | пользователь для SSH |
| `DEPLOY_SSH_KEY` | приватный ключ целиком, включая строки BEGIN и END |
| `DEPLOY_PORT` | порт SSH, если не 22 |
| `DEPLOY_PATH` | каталог развёртывания, например `/opt/multimessenger` |

Токен для реестра создавать не нужно: GHCR принимает встроенный `GITHUB_TOKEN`.

Рекомендуется завести окружение `production` (`Settings → Environments`) и включить в нём required reviewers — тогда выкатка будет ждать подтверждения человеком. Workflow на это окружение уже ссылается.

## Откат

Пайплайн откатывается сам, если приложение не ответило на `/health/ready` за две с половиной минуты: возвращает предыдущий образ и печатает последние сто строк логов.

Вручную:

```bash
MULTIMESSENGER_IMAGE=ghcr.io/aulrata/multimessenger:<sha> docker compose -f docker-compose.prod.yml up -d --no-deps app
```

Каждая сборка помечается тегом с хешем коммита, поэтому вернуться можно к любой.

## Проверка живости

| Ручка | Что проверяет | Кто дёргает |
|---|---|---|
| `/health/live` | процесс отвечает | HEALTHCHECK контейнера |
| `/health/ready` | доступны PostgreSQL и бакет MinIO | пайплайн после выкатки |

Разделение осмысленное: при недоступной базе перезапускать контейнер бессмысленно — перезапуск её не починит. Поэтому `live` не ходит в зависимости.

## Резервное копирование

Ежедневно в 03:30 таймер systemd запускает [backup.sh](../deploy/backup.sh): дамп PostgreSQL в формате custom, содержимое бакета MinIO, архив директории сессий. Готовая копия уезжает по rsync за пределы сервера.

**Копия обязана лежать не здесь.** Если `BACKUP_REMOTE` не задан, скрипт завершается ошибкой — намеренно. Архив рядом с данными не защищает ни от чего и создаёт ложное ощущение безопасности.

Установка:

```bash
sudo cp backup.sh /opt/multimessenger/ && sudo chmod 700 /opt/multimessenger/backup.sh
```

```bash
sudo cp backup.env.example /opt/multimessenger/backup.env && sudo nano /opt/multimessenger/backup.env
```

```bash
sudo cp multimessenger-backup.{service,timer} /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now multimessenger-backup.timer
```

Проверить, что таймер встал:

```bash
systemctl list-timers multimessenger-backup
```

Прогнать копирование прямо сейчас, не дожидаясь ночи:

```bash
sudo systemctl start multimessenger-backup.service && journalctl -u multimessenger-backup -n 50
```

### Восстановление

Проверять восстановлением обязательно — непроверенный бэкап бэкапом не является. На чистой машине:

```bash
docker compose -f docker-compose.prod.yml up -d postgres minio
```

```bash
docker compose -f docker-compose.prod.yml exec -T postgres pg_restore --username $POSTGRES_USER --dbname $POSTGRES_DB --clean --if-exists < postgres.dump
```

Содержимое MinIO и сессии распаковываются в соответствующие тома, после чего поднимается `app`.

### Что учесть

Файлы сессий равносильны полному доступу к аккаунтам менеджеров. Скрипт выставляет копиям права 600, но хранилище резервных копий должно быть не менее доверенным, чем сам сервер.

Уведомления о неудачном копировании пока не настроены: `OnFailure` в unit-файле закомментирован. Пока их нет, стоит раз в неделю заглядывать в `systemctl list-timers`.

## Чего пока нет

**Обратного прокси и HTTPS.** Приложение слушает `127.0.0.1:8080` и наружу не выставлено. Понадобится к этапу 3.2: вебхук MAX требует публичный адрес с валидным сертификатом. Кандидаты — Caddy (сам получает сертификаты) или nginx с certbot.

**Проверки миграций на обратимость.** Приложение применяет их само при старте; если миграция окажется ломающей, откат образа не вернёт схему. Пока схема одна и данных нет, это терпимо, но к моменту реальной эксплуатации стоит завести правило: миграции только совместимые вперёд-назад.
